Repo-specific notes for future Claude sessions. See README.md for what the tool does and how to use it.

## Architecture invariants — do not relax without a concrete reason

The shape was chosen after a multi-perspective design review converged on the smallest system that meets the goal. Don't add the components below without checking first:

- **No HTTP server.** SSH is the transport — it already provides auth, encryption, blocking-wait, cancellation. Don't add FastAPI.
- **No queue, no SQLite.** Concurrency is admitted via five kernel-backed file-lock primitives, not a queue service. `LaunchLock` and `UiClipboardLock` guard brief global critical sections. `ParallelSlot` caps whole-run concurrency; `ChromeActivityLease` is shared across whole browser-use lifetimes and therefore does not serialize users; `RunClaim` is per-run and excludes only duplicate ownership of that run_id. None stores a refcount or database state, and the kernel releases every lease on process death.
- **No daemon / launchd.** `tmux` is enough until something specifically demands persistence. Chrome itself is the persistence — once a worker (or `login`/`doctor`) launches it, subsequent workers connect over CDP to the same process. Workers never `browser.close()` Chrome; `gpt-pro-relay close-chrome` is the only authorized teardown.
- **One `launch_kwargs()`** in `cli.py` — `login`, `doctor`, and `_run` all use the *exact* same `_chrome_open_argv()`. Diverging flags = subtle auth drift. Only the *launching* worker exercises the flag set; followers `connect_over_cdp` and never re-launch, so flag drift is impossible by construction.
- **Real side-by-side Chrome Beta, not Stable Chrome or bundled Chromium.** Auth/anti-abuse behavior requires real Chrome, while the macOS app identity must be distinct from personal Stable Chrome. `DEFAULT_CHROME_APP` is `/Applications/Google Chrome Beta.app`; `GPT_PRO_CHROME_APP` may override it only with a recognized side-by-side Beta/Dev/Canary bundle identity. `validate_chrome_app` rejects `com.google.Chrome` fail-closed before killing or launching anything. A dedicated `--user-data-dir` isolates data but does **not** isolate LaunchServices/Dock identity.
- **Fail closed on model + reasoning.** Since the 2026-07 GPT-5.6 redesign the composer chip shows the reasoning-**effort** tier ONLY — the model is a separate axis with no chip signal (no aria-label, no dataset key, no hidden mirror text). So the two axes are gated separately: the pre-send chip verifies the *effort* and the post-send served-slug audit verifies the *model*. The fast path requires the chip to contain `"Pro"` — the top effort tier and the only one carrying that token (`is_pro_label`); model names never appear in the chip, so a substring test uniquely identifies the Pro tier. Use predicate matching (substring tests, not exact-string equality): ChatGPT relabels this chip across redesigns (bare `"Pro"` is current; `"Pro Extended"` / `"Extended Pro"` / `"Extended"` were earlier GPT-5.5-era labels). The desired model is **GPT-5.6 Sol**, whose served slug is `gpt-5-6-pro` (the UI display name "Sol" and the slug diverge — verified 2026-07-09 via a live send). Never *return* an answer from a model we haven't verified: a served slug outside `PRO_MODEL_SLUGS` is fatal.
- **The effort chip is verified at three points, not one — it's a time-of-check/time-of-use problem.** Reading the chip once after page load is insufficient: the pill hydrates optimistically to the persisted "Pro" and then an async resolution can re-resolve a new conversation's default to a lower effort tier within ~2.6s. (The GPT-5.5-era incident: run `ask-20260531T065451Z` logged `model_verified="Extended Pro"` yet was served `gpt-5-5-thinking`, ≈12% of runs — the mechanism survives the redesign, only the labels changed.) The three layers, all fail-closed: (1) **`read_composer_chip_text` requires a stable read** — the same non-placeholder label for `stable_polls` (default 3) consecutive ~0.2s polls; on timeout it returns `""` (never the last transient), so an oscillating chip fails the predicate. (2) **Pre-send re-verify** — immediately before the Send click, re-read the chip (a passive `inner_text()`, *no* `UiClipboardLock`, *no* menu) and `model_drift_before_send` if it isn't `is_pro_label`. Do NOT re-run the chip menu here (needs the lock, fragile Radix nav on a loaded composer) — fail closed and surface the run_dir. (3) **Served-slug audit** — after completion, read the served turn's `data-message-model-slug`; a present slug not in `PRO_MODEL_SLUGS` (an explicit allowlist = `{"gpt-5-6-pro"}`, *not* a `startswith` test) is fatal *regardless of* `completed`. A *missing* slug degrades fail-OPEN (returns `ok` with `model_audit: "unverified_missing_slug"` + a `served_model_unverified` stage) — making it fatal would brick the tool on a single attribute rename, the same blast radius the network-body-gate was rejected for. **The served-slug audit is now the *only* pre-return model check** — the chip carries no model signal, so `model_verified`/`model_reverified` confirm the *effort* only. But the slug encodes the *effort tier too*, not just the model (Sol+Pro → `gpt-5-6-pro`; Sol+High → `gpt-5-6-thinking`, measured 2026-07-09), so on a **present** slug the audit catches an effort downgrade *and* a model swap — closing the effort read→Send TOCTOU fail-closed (a dropped effort stamps a non-allowlisted slug → `served_model_mismatch`). Residual risks: a present-slug drift is caught only *after* a full Pro send is spent (then rejected → resubmit). **Rejecting the run is not enough — the artifact is named for its outcome** (see *Response artifact lifecycle* below): a rejected turn's text is complete and plausible, differing from a verified answer only by provenance, so leaving it at `response.md` invites a caller to return it anyway (2026-07-15: a caller hit `served_model_mismatch` and reasoned its way to reading `response.md` out of the run_dir to salvage the lens — the guard held; the artifact name didn't). The fatal verdicts publish `response.rejected.md`; the fail-open ones publish `response.md` normally, or a selector rename would brick the tool. When the slug is **absent** (an OpenAI attribute rename — on a *completed* turn the slug is stamped, so "missing" ≈ a rename, not a per-run flake), the chip proves neither model nor effort, so the audit falls back to an **independent read-only chip-menu model read** (`read_selected_model` → `classify_served_audit`): a *confirmed* non-Sol model is fatal (`model_menu_mismatch`), Sol confirms the model but leaves effort unverified (`model_ok_slug_missing`, fail-open), and only an unreadable menu keeps the bare `unverified_missing_slug` fail-open. So the one path that can still *return* a wrong-model answer as `ok` now requires **two** simultaneous selector breaks — the slug attribute AND the menu — plus a default drifted off Sol; making either fatal alone would brick on a single rename (the blast radius the network-body-gate was rejected for). **`doctor` is the standing drift detector**: it runs the same read-only model read (no send) and exits non-zero on a confirmed non-Sol default — run it after any manual profile poking. NB the composer *effort* default is a persistent profile preference (a stray non-Pro selection sticks across fresh pages until reset; the send-path slow path re-selects Pro each run, but `doctor` flags it). Regression tests in `tests/test_chip_read.py` (`is_pro_label` + `classify_model_status` + `doctor_exit_ok` + `classify_served_audit`), `tests/test_chip_submenu.py` (the 2026-08-28 flat menu: the slow path drives the Power *slider* to its max tier via click-then-`End` — never the removed named-effort radio — and fails closed if the slider never maxes or the chip never settles on Pro; plus the direct flat-list model read), and `tests/test_page_recovery.py` (the artifact lifecycle: each outcome publishes its own name — fatal verdicts, fail-open, timeout, and a close mid-audit that must publish nothing).

## ask / fetch / _run — the submit-and-wait architecture

`ask` does NOT drive the browser directly. It's a supervisor:

1. Read prompt from stdin, validate `--run-id` (or generate one).
2. If run_dir exists with same `prompt_sha256` → attach (no respawn). With different sha → exit 2 `run_id_conflict`.
3. Otherwise: write `prompt.md` and `meta.json` atomically, emit a `submitted` JSONL line on stderr, spawn a detached `_run` worker via `subprocess.Popen(..., start_new_session=True, stdin=DEVNULL, stdout/stderr → run_dir/worker.{stdout,stderr})`.
4. Poll `result.json` until terminal. The default wait is indefinite; an explicit `--generation-timeout` bounds only the parent wait and never stops the detached worker.
5. On terminal `ok`: print `response.md` to stdout, terminal JSONL to stderr, exit 0.

`_run` (hidden subcommand) reads `run_dir/prompt.md`, runs the Playwright flow, writes `response.md` and `result.json` atomically. It survives `SIGHUP` because `start_new_session=True` puts it in its own session — that's how SSH-drop recovery works. **Do not catch `SIGHUP`** in the worker; the survival depends on it.

`fetch <run-id>` reads `result.json` (polling if not yet present, with `--timeout`). Same dispatch logic as the parent's post-wait. `--timeout 0` is a non-blocking check.

The split is the recovery story: if the parent (or the SSH session containing it) dies, the worker keeps running. The agent reconnects with the same `--run-id` and either re-runs `ask` (idempotent attach) or runs `fetch`. Never re-submit a fresh prompt — that costs another 5–20 min of Pro reasoning.

## stop — graceful interrupt via a file signal (worker-driven, no browser drive by the command)

`stop <run-id>` interrupts a run. It is a **producer only**: it writes `run_dir/stop.request` (the whole signal is the file's existence — no server, no queue, no new lock, matching the file-primitive invariant) and reports the outcome; it **never drives the browser**. The **owning worker** consumes the signal at its phase gates, because it holds the page handle and the `RunClaim` — so tab-ownership, concurrency isolation, and single-writer all stay intact (an external process grabbing the tab would break all three). Consumption points, all fail-safe (`stop_requested()` is a cheap `exists()` the polling loops already run):

- **Queued** — `ParallelSlot.__enter__`'s wait loop checks `stop_check` each poll and raises `RunStopped` → dequeue before acquiring a slot (no Pro reasoning). `_browser_run` also checks once before the slot (stop requested before start).
- **Pre-send** — one check immediately before the single `send_btn.click()` (next to the pre-send chip re-verify). A stop that lands after the click is caught post-send instead; the only uncovered window is the click itself, which is safe (a sent turn is stopped mid-flight rather than dequeued — never a double-send).
- **Post-send** — `_monitor_and_finalize`'s loop (~1.5s cadence) clicks ChatGPT's Stop button (`_click_stop_button`, same selector `_stop_button_count` reads) and finalizes. A close during the click raises `RunPageClosed` → the recovery loop re-enters and re-observes the still-present signal.

**Discard policy (chosen):** a stopped run publishes **no** response artifact — `result.json` `status: "stopped"` (`reason: stopped_before_send | stopped_after_send`, worker exit 5) is the authority. `_emit_terminal` returns 5 and prints nothing on stopped (so `fetch` on a stopped run yields no body). Nothing is extracted; a diagnostic `stopped.png` + `final.html` survive for the after-send case.

**Dead-worker case (worker-only v1):** if no live worker consumes the signal, `cmd_stop` reports it rather than attaching itself. It is **wait-first, then a non-contending process check** — deliberately NOT a `RunClaim` probe: the worker acquires that claim once, non-blocking, and reads a failed acquire as "another worker owns this" and exits, so transiently holding the claim as a liveness probe could make a *just-starting* worker abort and orphan the run. So `cmd_stop` waits for a terminal `result.json` up to `--timeout` (default 30s); on a result it reports (and clears the now-inert signal); on timeout it runs `_worker_process_alive` (an escaped, boundary-anchored `pgrep -f 'gpt_pro\.cli _run <id>'` that can't touch the claim) → alive ⇒ `pending`, else re-check `result.json` for a just-finished race, else `no_live_worker` (exit 2) + manual CDP path. External attach-and-stop was **deliberately not built** — it would break tab-ownership isolation and lean on the `conversation.json` breadcrumb the recovery design forbids for cross-process use. Revisit only if orphaned generations become common. `cmd_stop` exits: 0 stopped/already-finished/pending · 2 no_live_worker · 4 not_found. Regression tests: `tests/test_stop.py` + `tests/test_page_recovery.py::test_monitor_stops_after_send_on_signal`.

## Post-send page-close recovery — an *in-process* layer, distinct from the SIGHUP story

The SIGHUP story above covers the *parent/session* dying while the worker lives. A different failure is the worker being **alive but blinded**: the user closes its Chrome tab/window mid-run. Then `page.evaluate` raises `TargetClosedError`; before recovery existed, the old code swallowed it as empty text until the then-current generation cap. `_run_with_browser` now recovers **in-process** — nothing on disk drives this (the worker holds the conversation URL in memory; `conversation.json` is a diagnostic breadcrumb only, and no code re-spawns `_run` from it — do not build cross-process resume on it without a separate design that re-checks the no-resubmit contract).

Load-bearing invariants (regression tests: `tests/test_page_recovery.py`):

- **Never resubmit — enforced structurally, not just by test.** The extracted `_monitor_and_finalize(page, ...)` receives **no** `prompt_text`, composer, or send locator, so it is *incapable* of pasting/sending. There is exactly one reachable `send_btn.click()` and the entire recovery loop lives strictly *after* it. Don't thread the prompt/composer into the post-send helper "for convenience" — that reopens the duplicate-submission hole.
- **`RunPageClosed` punches through the swallow-to-sentinel helpers.** `served_assistant_model_slug` / `_copy_button_present` / `_copy_button_extract` / `read_selected_model` / `read_latest_assistant_text` / `_stop_button_count` each catch exceptions and return a sentinel (None/False/""/1) — but only on a *live* page (`page.is_closed()` false). A close **raises `RunPageClosed`** instead. This closes a real hole: a close during the served-model audit would otherwise degrade to `slug None + menu None → unverified_missing_slug` (fail-open) and return a wrong-model turn as `ok`. Keep the sentinel for genuine live-page selector misses; keep the close raising.
- **The discriminator is `page.is_closed()` + `ctx.new_page()` success, never error-text matching.** A closed tab and a dead browser both raise `TargetClosedError`; matching the string is version-fragile and violates the repo's substring/predicate convention. On a detected close the recovery loop opens a fresh tab in the *same* context — success proves tab-level close (recover); failure is `browser_disconnected_after_send` (terminal, and it does **not** relaunch Chrome under sibling workers).
- **There is no production generation deadline.** `DEFAULT_GENERATION_TIMEOUT` is infinite, so a legitimate long Pro turn can finish naturally. The existing absolute-deadline plumbing remains because finite injected deadlines make recovery behavior testable, but production never spends that branch. The ambiguous-click rule is unchanged: a click can dispatch the request and *then* raise on close, so recover if a URL was captured; otherwise return `send_outcome_unknown`, and never resend.
- **Recover only a validated `https://chatgpt.com/c/<id>`** (`parse_conversation_url`: exact host — rejects credentials/ports/foreign hosts — and an exact `/c/<id>` path, query/fragment stripped). Captured via a synchronous `framenavigated` observer (Playwright 1.58 routes `Page.navigatedWithinDocument` through same-document frame navigation, so `history.pushState` fires it) **and** a `page.url` poll in the monitor loop; immutable once set (a stray redirect can't repoint it). No sidebar/"most recent" fallback — that breaks concurrency isolation. After nav, URL equality is necessary but not sufficient: also confirm auth survived and a message turn actually rendered (`shell_missing`).
- **Cleanup rebinds the owned page.** The recovery loop lives in the extracted `_run_postsend`, which returns `(result, latest_owned_page)`; `_run_with_browser` assigns `result, page = await _run_postsend(...)` so the existing bounded `finally: page.close()` always targets the latest tab and the old (closed) one can't leak. Still no `browser.close()`; still only ever closes this worker's own tab. (The extraction exists so the recovery control flow — rebind, `closed_during_nav`, terminal reasons — is unit-testable with fakes; `tests/test_page_recovery.py`.)
- **Every recovery operation is locally bounded.** Opening a page, navigation, viewport pinning, auth checks, and shell detection retain finite operation-specific timeouts, so a broken recovery attempt fails rather than hanging even though the generation as a whole is unbounded.
- **`conversation_drift` is a fail-closed guard against post-recovery redirection.** `_recover_navigate` validates the conversation once; `_monitor_and_finalize` re-asserts `parse_conversation_url(page.url) == conv.get()` before extraction/audit so that if the reopened background tab is later navigated to a *different* `/c/<id>` (e.g. a human grabs it), the worker returns `conversation_drift` rather than extract and return another conversation's answer as `ok`. `page.url` is a cached Playwright property (no channel round-trip, never raises on a closed page — verified against the pinned 1.58 source), so this check and the post-send `conv.capture(page.url)` polls are safe; the actual close-detector is `page.evaluate` in `read_latest_assistant_text`, which *does* raise → `RunPageClosed`.
- **Bounded to `MAX_PAGE_RECOVERIES` (3).** The minimal policy for the observed accidental Cmd-W is 1; 3 tolerates a fumbled repeat close while finite per-operation timeouts keep each attempt bounded. `classify_recovery` retains its finite-deadline branch for regression tests (`no_url` / `deadline` / `exhausted` / `recover`), although production supplies an infinite deadline.

**Unproven premise, flagged not resolved:** whether reopening a *mid-flight* Pro conversation resumes live DOM streaming, only shows the finished turn after server completion, or (worst case) shows a frozen partial that never updates — is server/UI behavior no unit fake can prove. The Copy-button completion gate + served-model audit ensure a frozen partial is never returned as an answer, but without an overall deadline that run must be interrupted explicitly with `stop`. If live testing proves a frozen-partial-no-resubscribe case, the follow-up is locally-bounded read-only *reload* polling of the captured URL — never a Continue/Regenerate/Send click.

## Atomic writes

Use `atomic_write(path, content)` for `prompt.md`, `meta.json`, `response.pending.md`, `result.json`. Pattern: write `path.tmp`, then `os.replace(tmp, path)` (POSIX atomic). `fetch` reads `result.json` concurrently with the worker writing it, so the rename guarantees a consistent read. (The answer body is `atomic_write`n to `response.pending.md` and reaches its final name via `publish_response` — never `atomic_write` it straight to `response.md`; see below.)

## Response artifact lifecycle — the name is the verdict

**`response.md` means exactly one thing: a completion-gated body the audit did not reject.** Note what that is *not* — it is **not** "model verified": the fail-open verdicts (`unverified_missing_slug`, `model_ok_slug_missing`) return `ok` by design and so publish canonically. `status: ok` + `model_audit` together are the guarantee; the filename alone only tells you the audit didn't *reject* it. Extraction stages to `response.pending.md`; `publish_response(run_dir, name)` renames it once — and only once — the outcome is known:

| outcome | published name |
|---|---|
| `status: ok` (completed, audit not fatal — incl. the fail-opens) | `response.md` |
| fatal model audit (`slug_mismatch` / `menu_mismatch`) | `response.rejected.md` |
| attachment-only task acknowledged/planned instead of executed (`instruction_boundary_lost`) | `response.incomplete.md` |
| legacy `status: timeout` from a worker created before the cap was removed | `response.partial.md` |
| raised after staging, before any verdict (page close → `RunPageClosed`) | stays `response.pending.md` |
| returned/raised **before** staging (`conversation_drift`, a pre-extraction close) | none — the run publishes nothing |

So a run leaves **at most one** of these, not exactly one.

This is structural, and it exists because **the text is not self-describing**: a wrong-model turn is complete and plausible, and a "partial" is not visibly partial — the Copy-button gate is exactly what catches a Pro thinking-summary that reads as a finished short answer (cf. `reframe-review-040`). So the *name* is the only signal a caller reading a run_dir gets, and every non-answer must carry a name that says so. Publishing late (rather than writing `response.md` up front and renaming on failure) is what closes the pre-verdict window: a crash between extraction and the audit would otherwise leave an **unaudited** answer at the canonical name. Staging keeps the diagnostic without ever claiming to be the answer — don't "simplify" this back to an eager write plus a rename.

**`result.json` is still the authority: `status: "ok"` is what makes `response.md` usable.** `_emit_terminal` reads `response.md` only on `status: ok`; nothing reads the other four. The rejected/incomplete/partial/pending paths are deliberately **not** reported as result fields — `run_dir` plus a fixed name locates them for a human, while a `*_response` field hands an automation agent the exact salvage target it must not read.

## Selectors — expect breakage here

ChatGPT changes these without notice. Current truth (verified via `gpt-pro-relay doctor` artifacts):

- Effort chip (composer-embedded): `button.__composer-pill[aria-haspopup="menu"]` — **unchanged through the 2026-08-28 redesign** (each redesign rebuilds the *menu*, not the chip). Since the 2026-07 GPT-5.6 redesign its visible text is the reasoning-**effort** tier only — bare `"Pro"` means the top tier (`is_pro_label` = contains `"Pro"`); the **model is NOT in the chip**. The chip's SSR text is `"Model"` until React hydrates; and while the menu is **open** the chip renders the generic label `"Thinking effort"`, showing the committed tier only once the menu closes — so read the chip for verification with the menu dismissed. There is no separate top-bar model picker (removed in the 2026-04 redesign).
- **Chip menu is a single flat "Power slider + model list" menu (2026-08-28 redesign; verified live 2026-08-28).** The 2026-08-06 two-level "Model →/Effort →" submenu is **gone** — there are no more `aria-haspopup="menu"` rows and no "Advanced" toggle. Clicking the chip opens ONE menu (`data-testid="composer-intelligence-picker-content"` is **back**), in its default `data-view="simple"`:

  ```
  [role=menu][data-state="open"]
    role=menuitem       aria-label="Power"          -> the effort SLIDER handle; wraps
                                                        role=slider aria-valuemin=0 aria-valuemax=4,
                                                        aria-keyshortcuts="ArrowLeft ArrowRight".
                                                        Value 0..4 = Instant/Medium/High/Extra High/Pro;
                                                        announcement (.d1BZWq_KeyboardAnnouncement)
                                                        reads "Pro, 5 of 5." / "Instant, 1 of 5."
    role=menuitemradio  "GPT-5.6 Sol"                -> model list, FLAT in this menu (no submenu).
    role=menuitemradio  "GPT-5.5"                       aria-checked marks the account default.
    role=menuitem       aria-label="Select model"    -> simple<->advanced view toggle
  ```

  **Effort is now DRIVEN BY THE SLIDER, not a named `menuitemradio`** (the removal of that radio is exactly what broke the old code → `chip_menuitem_missing` → `model_select_failed`, all runs with a non-Pro chip). `ensure_pro_chip`'s slow path opens the menu and calls `_drive_power_slider_to_max`: **CLICK the `[aria-label="Power"]` menuitem, then press `End`.** Two things are load-bearing and both were verified live: (1) **the click commits, a bare focus does not** — `power.focus()`+ArrowRight moves `aria-valuenow` transiently but the selection **reverts on reload**; the click engages the committed interaction, and `End` then drives to the top tier from any starting position. The inner `role=slider` node is `tabindex=-1 aria-hidden` — do NOT target it; target the Power menuitem. (2) **Verify by BOTH signals, both fail-closed:** the slider value (`aria-valuenow == aria-valuemax`, read via `SLIDER_STATE_JS` off the open menu — robust to tier renames / notch-count changes) AND, after dismissing the menu, the chip label reading `is_pro_label` (the name-anchored gate — that is what "the top tier is Pro" means, and it fails closed if the top tier ever stops being labeled "Pro"). Reading the slider value off the menu with `evaluate` (not a per-element `get_attribute`) means a vanished slider returns `null` and fails closed instead of hanging on an actionability wait. **The chip is still a TOGGLE** — clicking it while open closes it — so `_open_chip_menu` checks `aria-expanded` before clicking, and `_drive_power_slider_to_max` waits on `[role=menu][data-state="open"]` (`OPEN_MENU`).

  **Model reads are now a direct radio read** (`read_selected_model` → `SELECTED_MODEL_JS`): the checked `[role="menuitemradio"][aria-checked="true"]` is directly in the open menu, no submenu navigation. No checked radio → `None` → the fail-**OPEN** `unverified_missing_slug` verdict (`doctor` "unknown"). The old submenu-ownership hazard (a stale exit-animating menu being read as the model) is gone with the submenu itself.
- **`ensure_pro_chip` still deliberately does not correct the *model*.** The model is a persistent account preference (a fresh chatgpt.com defaults to Sol) and is verified fail-closed by the served-slug audit, so self-correcting it would add work for a rare, audit-caught drift. **The rate is measured, not assumed:** first live instance 2026-07-15 — run `ask-20260716T034413Z` served `gpt-5-5-pro` while the chip read `"Pro"` at both check points, **1 of 379 runs** since the 2026-07-09 Sol switch. Its three siblings, dispatched within 8s in the same burst, all served `gpt-5-6-pro` — **consistent with per-conversation drift, and an argument against a *stably* flipped account preference** (which would have taken the whole burst). It does not rule out a transient preference race or server-side routing, so don't dismiss profile state when debugging the next one; check the siblings first, then `doctor`. That rate is the argument for keeping this decision.
- **Prior redesigns reset the persisted effort preference off Pro** (2026-08-06 → `Medium`; the 2026-08-28 redesign was observed with the chip at `Instant`), which is why the slow path exists and runs every non-Pro run. `doctor` goes red `misconfigured` on such a page — the system working. Sol+Pro still serves **`gpt-5-6-pro`** (re-verify end-to-end after this redesign; `PRO_MODEL_SLUGS` unchanged). The model list is now `GPT-5.6 Sol / GPT-5.5` (o3 dropped).
- Composer: `page.get_by_role("textbox").first` (works for textarea or contenteditable; the underlying `id="prompt-textarea"` is the contenteditable)
- Send button: `[data-testid="send-button"]` is still primary; resilient fallback is `button[aria-label="Send prompt"]` / `button[aria-label="Send message"]`. Send button is only mounted when composer has content — never assert it before pasting.
- Assistant messages: `[data-message-author-role="assistant"]`
- Copy button (extraction): `[data-testid="copy-turn-action-button"]` inside the assistant message's `[data-testid^="conversation-turn"]` container.
- "Too many requests" rate-limit modal: `[data-testid="modal-conversation-history-rate-limit"]`, a Radix `role="dialog"` (title "Too many requests") whose dismiss button is a bare `<button>Got it</button>` (no testid — matched by accessible name `"Got it"`). See the auto-dismiss note under *Other fragile assumptions*.
- Product-announcement "beacon" modal: `#modal-beacon` / `[data-testid="modal-beacon"]` is the mount point; inside it a Radix `role="dialog"` with its own `[data-testid="close-button"]` (`aria-label="Close"`) and a primary CTA. Auto-dismissed via the **close button, never the CTA**. See the same note.

When `_run` starts failing with `model_select_failed`, the screenshots + `error.html` in `~/.gpt-pro/runs/<run_id>/` are the diagnostic. The `error.html` is `page.content()` at the moment of failure — grep it for testids and aria-labels to find the new selectors before patching blind.

## Other fragile assumptions

- **Login detection** uses cookie prefix `__Secure-next-auth.session-token` (NextAuth chunked cookies — `.0`, `.1`). If OpenAI changes their auth scheme, update `SESSION_COOKIE_PREFIX`.
- **Completion detection requires three signals**: text stable 5s + no Stop button + Copy button mounted on the latest assistant turn (`[data-testid="copy-turn-action-button"]` inside the `[data-testid^="conversation-turn"]` container). The Copy button is the affirmative gate — the turn-action toolbar only renders after the turn is finalized. The text-stable + no-Stop heuristic alone false-positives on Pro runs: the "thinking summary" panel renders text that sits stable for tens of seconds while the model continues reasoning silently, with no Stop button visible (this caused run `reframe-review-040` on 2026-04-30 to return a 228-char summary fragment after only 234s on a 236KB-prompt task). If the Copy button selector changes, the run waits indefinitely rather than returning a partial; stop it explicitly and patch the selector, don't loosen the gate.
- **Post-send landing gate — `sent` is not proof the message submitted.** `log_stage("sent")` fires as soon as `send_btn.click()` returns without raising, but a click can *return and still no-op*: ChatGPT silently ignores Send while a pasted-text **upload attachment** is still finalizing (the `:not([disabled])` wait clears when the button *mounts*, not when the upload completes), and parallel bursts drop sends too (observed 2026-07-18: 2 of a 4-way burst of ~10k-char prompts no-op'd — composer still full, URL still `/`, no turn). A no-op Send is **indistinguishable to the monitor loop from a Pro model thinking silently**, so the old code spun the full 60-min `--generation-timeout` on a dead page. `_monitor_and_finalize` now opens with `_confirm_send_landed` (`SEND_LANDING_TIMEOUT`, default 20s): landing = a captured `/c/<id>` URL **or** a rendered user turn **or** a Stop button; none within the window → **fail closed `send_did_not_land`** (surface `run_dir`, publish nothing — it returns before staging). **No auto-retry** — resubmitting burns 5-20 min of Pro reasoning; the caller resubmits (a proven no-op means nothing was sent, so a fresh submit is safe, unlike the ambiguous-close case). The signals are ORed and read-errors bias toward "landed" so a lagging URL capture never false-fails a good send (a false "landed" just reverts to the old monitor-then-timeout; a false "not-landed" would waste a Pro send). On a recovery re-entry `conv` is already set → instant no-op. A close during the gate raises `RunPageClosed` → the recovery loop. Regression tests: `tests/test_page_recovery.py` (`_confirm_send_landed` + `test_monitor_fails_closed_on_send_not_landed`). **Do not** thread the prompt/composer into the gate to "resend on no-op" — that reopens the duplicate-submission hole the post-send helpers are structured to prevent; fail closed and let the caller decide.
- **"Too many requests" modal is auto-dismissed, not a rate limit on generation.** A parallel burst throttles the *conversation-history* endpoint (`/backend-api/conversations` → 429, the same 429s already in `network.json`) and ChatGPT renders a full-viewport `fixed inset-0 z-50` modal (`data-testid="modal-conversation-history-rate-limit"`, dismiss `<button>Got it</button>`). It is **not** a model/usage cap — the Pro turn keeps generating underneath (measured: 15 runs showed it, 13 still finished `ok`). Its only harm is the `pointer-events: auto` backdrop: a worker that reaches `composer.click()` while it is up hangs the full 30s actionability timeout → `worker_exception` (2026-07-19, 2 runs died `TimeoutError … waiting for get_by_role("textbox")` — root cause invisible in the logs, only in `error.html`), and it steals focus from a human on the shared Chrome. `_install_rate_limit_dismisser` registers a Playwright **locator handler** (`page.add_locator_handler`) — on the initial tab *before* `goto` and on every recovery replacement tab, mirroring `_attach_response_logger` — that clicks "Got it" before the actionability checks of every downstream click (chip-menu, composer, send, Copy), logging `rate_limit_modal_dismissed`. Safe w.r.t. `_focus_and_paste` **only because the paste is locator-bound**: the handler only fires at an action's actionability checkpoint, and a bare `page.keyboard.press("Meta+V")` has none — so a modal mounting in the gap between `composer.click()` and the paste (a list-fetch 429 during the synchronous `pbcopy`) would steal focus and the paste would land in the modal. `_focus_and_paste` therefore pastes via `composer.press("Meta+V")` (the composer *locator*), which re-runs the dismiss handler and re-focuses the composer immediately before dispatching the same Meta+V that hits ProseMirror's native paste. Do **not** revert that to `page.keyboard.press` (regression: `tests/test_rate_limit_modal.py::test_focus_and_paste_uses_locator_press_not_bare_keyboard`). It is a **UI-overlay cleaner, NOT rate-limit backoff** — it never resubmits or re-spends Pro reasoning (the distinction the "intentionally NOT built" backoff bullet draws); the cause-side lever for the throttle itself is still lowering `GPT_PRO_MAX_PARALLEL`. Fail-open on both drift modes: a genuine `add_locator_handler` API failure is swallowed to `rate_limit_dismisser_install_skipped` (a Playwright API change can't brick the send path), while a **selector rename does not throw at all** (locators are lazy) — it silently leaves the handler inert, reverting to the pre-fix burst-stall (`doctor`/`error.html` surface it). Neither aborts the send. Already-running workers can't pick up the handler; dismiss their live cards out-of-band by connecting `connect_over_cdp` to port 19222 and clicking "Got it" per tab. Regression tests: `tests/test_rate_limit_modal.py`.
- **The rate-limit modal is not the only blocking overlay — a product-announcement "beacon" does the same thing, and needs its own handler.** 2026-08-08: run `ask-20260808T010319Z-d6177828` died `worker_exception` on the **send** click — past paste, past both chip verifications, one step from submitting — because "You now have access to Health in ChatGPT" had mounted the same `fixed inset-0 z-50` / `pointer-events: auto` overlay, this time inside `#modal-beacon`. The rate-limit handler is **inert** against it (different test-id, and locators are lazy so nothing complains), which is the whole lesson: each modal test-id needs its own handler, and the *symptom* is identical — a 30s actionability timeout whose root cause is visible only in `error.html`. **Two** runs died with that beacon open (`data-state="open"`) in their `error.html`: the 08-08 one names the beacon subtree as the interceptor, and `ask-20260801T000235Z-00f583c6` died earlier on the *composer* click with only the bare `waiting for get_by_role("textbox").first` log — the same uninformative signature already recorded for the 2026-07-19 rate-limit deaths, so treat it as the same class rather than independently proven. Rate is **2 of the 678 runs since 2026-08-01** (the window this announcement has existed), not 2 of the ~3400-run archive. When counting a modal like this, scan `error.html` across run dirs — not just `result.json` exception text — or you undercount every case whose log never names the overlay (that undercount is exactly how the first version of this note claimed one occurrence). Unlike the rate-limit modal it is **not** self-inflicted by parallelism, so lowering `GPT_PRO_MAX_PARALLEL` does nothing. `_install_beacon_modal_dismisser` mirrors the rate-limit handler with two deliberate differences: (1) **the trigger is the close BUTTON, not the `#modal-beacon` container** — the container is a mount point that can exist without a rendered dialog, and a handler that fires with nothing to click raises *inside the handler*, which Playwright propagates into the triggering action (turning a fail-open cleaner into the send failure it exists to prevent); keying on the button makes trigger and affordance the same element. `.first` is only a strict-mode guard. (2) **Close, never "Get started"** — the CTA also dismisses the dialog but opts the account into the announced feature. Both dismissers install through one entry point, `_install_modal_dismissers`, called on the initial tab and every recovery tab; adding a third modal means adding it there, not at the call sites. **Known limit, shared with the rate-limit handler and deliberately not fixed:** a dismiss click that is *itself* obstructed raises into the triggering action, and that error then resurfaces on later page calls (measured against real Playwright 2026-08-09) — a 5s abort rather than the pre-fix 30s stall. The plausible trigger is a rate-limit modal and a beacon stacking; never observed, and the best-effort alternative (swallow the click error + `no_wait_after`) measured *worse* — the handler spins dozens of times and the send still never lands. Handlers run one at a time in registration order (rate-limit, then beacon), so ordering is the axis, not concurrency. **If stacking is ever observed, the candidate fix is `locator.dispatch_event("click")`** (from the 2026-08-09 GPT review, which prototyped it in a real stacked-overlay fixture and cleared both overlays): event dispatch skips pointer hit-testing so it reaches a covered dismiss button, still scoped to the right element and still never resubmitting. Verify ChatGPT's React handler treats a dispatched event like a real click before adopting it, and keep the failure re-raising rather than swallowed. Regression tests: `tests/test_rate_limit_modal.py`, including a real-browser test gated behind `GPT_PRO_BROWSER_TESTS=1`.
- **Anti-detection flags** (`--disable-blink-features=AutomationControlled`, dropping `--enable-automation` and `--no-sandbox`) are load-bearing. Removing them triggers ChatGPT's auth-error redirect.
- **`Chrome CDP not ready on port 19222 after 30s` on a *newly installed* Chrome app is a macOS pre-execution hold, not the relay.** Diagnostic signature (measured 2026-08-06 on the Beta migration): the Chrome process **exists** with the correct argv but sits at ~32K RSS, 0% CPU, with `sample` showing a single frame `_dyld_start` and `vmmap` showing only the main executable + `dyld` mapped — *no* libraries, so it is not slow, it is blocked before linking. Bundle-wide, not Chrome-specific: `chrome_crashpad_handler --help` from the same bundle hangs identically, which is the cheap 15-second discriminator. Misleading signals: `spctl -a` returns `accepted` and `codesign -v` returns `valid on disk` — both speak to *signing policy*, not to pending first-open consent — and the unified log is silent. **Most likely Gatekeeper first-open consent** (macOS requires human approval to open downloaded software; an SSH-detached worker cannot answer that prompt), but `_dyld_start` is not Gatekeeper-specific — AMFI enforcement or an Endpoint Security authorization hook stops execution at the same boundary. Treat the attribution as unconfirmed: **the 2026-08-06 incident changed two variables at once** — `xattr -cr` and a human approval click landed in the same window — and, note, the *narrow* `xattr -dr com.apple.quarantine` was tried first and did **not** release it, so the obvious minimal remedy is not the known-good one either. Prescribe the interactive first launch (README *Troubleshooting*), not `xattr -cr`: `-c` clears *every* attribute on *every* bundle member, a wider bypass than the problem warrants. To actually settle it, reinstall a fresh quarantined bundle and change one variable at a time, recording `xattr -lr`, the exact dialog, and unified logs for `syspolicyd`/`amfid`/`taskgated`. Applies to any re-install or a switch to another side-by-side channel via `GPT_PRO_CHROME_APP`.
- **Extraction prefers the Copy button** via `[data-testid="copy-turn-action-button"]` (clean markdown), then `pbpaste` reads the system clipboard; falls back to `innerText` if either step fails. Result captures `extraction: "copy_button"|"innertext"` so you can audit which path won. Math, code fences, and tables are mangled under `innerText` — the fallback is only for degraded environments.
- **Concurrency model: shared Chrome + multi-tab + five locks.** `~/.gpt-pro/browser.lock` no longer exists. The flow is:
  - `RunClaim` (`~/.gpt-pro/claims/<run_id>.lock`) — the single-writer claim on one run_id, and the only lock that is *per-run* rather than global. `ask` holds it **briefly** across the exists/prompt_sha decision (a check-then-act: without it two concurrent same-run-id submits both conclude "new" and spawn a worker each onto one run_dir — verified by forcing the schedule: both threads land in the create block and collide on `atomic_write`'s shared `.tmp`, and GPT's repro had one worker publish the *other's* wrong-model body under its own `ok`). `_run` then holds it **for the whole run**, non-blocking, which is what makes the artifact lifecycle's single-writer premise structural; a second worker fails the acquire and exits touching nothing (writing `result.json` would race the owner's verdict, and the owner's result is what the loser's parent is polling for anyway). **`ask` MUST release before spawning** — the worker takes the same lock, so holding it across the spawn makes every worker lose to its own parent; `tests/test_run_claim.py` pins that ordering, and releasing early is safe because `meta.json` has already made the decision durable. Per-run, so two different runs never serialize.
  - `ParallelSlot(N)` (`~/.gpt-pro/slots/slot-*.lock`) — file-lock semaphore admitting at most `GPT_PRO_MAX_PARALLEL` (default 6) concurrent `_run` workers. Held for the entire run; the cap exists because parallel bursts on one ChatGPT Pro session are an account-side anti-abuse signal — raising it further is a knob, not a default. Polls every 2s when full and emits one `slot_queued` JSONL on entry to a wait, then `slot_acquired` with `waited_secs`.
  - `LaunchLock` (`~/.gpt-pro/launch.lock`) — serializes the CDP probe + conditional `open -n -a` launch/recovery path and the final kill inside `close-chrome`. Re-probes inside the lock to absorb double-launch races. `_kill_chrome_orphans()` runs only on launch recovery or explicit shutdown — never on the healthy connect path.
  - `ChromeActivityLease` (`~/.gpt-pro/chrome-activity.lock`) — every worker, `login`, and `doctor` holds a shared flock for its complete browser-use lifetime. Workers acquire it **before** `ParallelSlot`, so a worker blocked behind exclusive shutdown cannot take a slot and spuriously defeat that shutdown. Normal `close-chrome` attempts the same flock exclusively and non-blocking before taking `LaunchLock`; once exclusive, no new user can enter the old check-to-kill race. Contention returns `browser_in_use` without touching Chrome. `--force` deliberately bypasses a contended activity lease and can disconnect active users. Lock order is activity lease → optional parallel slot → `LaunchLock`, never the reverse. **The wedged-Chrome recovery kill takes this lease exclusively too** — see the recovery bullet below; `close-chrome` is *not* the only path that kills Chrome, and it was the only one holding the lease until 2026-08-06.
  - **Wedged-Chrome recovery is self-skipping, not burst-proof.** When the CDP probe genuinely fails, the launching worker re-probes inside `LaunchLock` and, before killing+relaunching, calls `_slots_held(skip_slot_id=<own>)` to refuse the kill *only* if **another** worker still holds a slot (its tab might be live). The `skip_slot_id` is load-bearing: a worker calls `ensure_shared_chrome_running` from inside its own `ParallelSlot`, and flock conflicts even across two fds in one process, so without the skip a worker counts its own slot and **no** wedged-Chrome recovery ever fires — even a lone serial run (the 2026-06-01 `worker_exception` deadlock; fixed in `8a3503d`, regression in `tests/test_slots_held.py`). Consequence for a parallel burst on a genuinely-wedged Chrome: workers serialize on `LaunchLock`, each fails its ~7s re-probe and **releases its slot on the raised `RuntimeError`**, so the *last* worker through the lock sees its siblings gone and recovers+relaunches. Net outcome is **N−1 failures + 1 success with Chrome restored**, not full auto-recovery and not a total deadlock — resubmit the failures. (A transient stall, by contrast, makes the re-probe succeed and nobody kills.) Letting a *confirmed*-wedged CDP kill regardless of held slots — recovering all N — was considered and declined: the re-probe is a weak transient-vs-permanent discriminator, no-auto-retry means it can't rescue the lost prompts anyway, and `close-chrome --force` is the manual escape hatch. Revisit only if burst-on-wedge becomes frequent.
  - **`_slots_held` is NOT sufficient to authorize that kill — `login` and `doctor` hold an activity lease and take no slot.** Found by review 2026-08-06 and confirmed by test: a slot-only guard let a worker `_kill_chrome_orphans()` out from under a human halfway through signing in, which is exactly the race `5a497de` closed for `close-chrome` and left open here. Recovery now *also* requires `ChromeActivityLease.held_by_this_process().try_upgrade_exclusive()`, and holds the lease **exclusively across the kill+relaunch** — proving sole use and keeping the check-to-kill window shut, the same property `close-chrome` gets from the same lock. Three things are load-bearing: (1) **it must convert the caller's own fd**, never open a second one — flock conflicts across two fds in one process, so a fresh fd would report contention against our own `LOCK_SH` every time and block recovery even for a lone serial run (the `_slots_held` self-count trap in a new costume). (2) **Non-blocking**, because the caller already holds `LaunchLock` while `close-chrome` takes the lease *before* `LaunchLock` — a blocking wait closes that cycle into a deadlock. (3) flock conversion is **not atomic** (the kernel drops the shared lock before taking the exclusive one), so the failure path re-takes `LOCK_SH` *non-blocking* — blocking there reopens the same deadlock against a `close-chrome` that slipped into the gap. A process holding **no** lease fails closed rather than killing. Burst behavior is unchanged: a losing worker releases its lease along with its slot on the raised `RuntimeError`, so the last worker through still recovers (N−1 + 1). Regression tests: `tests/test_chrome_activity_lease.py` (lease-only user blocks the kill · sole user still recovers · no-lease fails closed · the exclusive window actually excludes a new user and the downgrade readmits one).
  - `UiClipboardLock` (`~/.gpt-pro/clipboard.lock`) — held across the foreground+focus+`pbcopy`+`Meta+V`+restore transaction in `_focus_and_paste`, and across the baseline-`pbpaste`+click-Copy+post-`pbpaste`+restore transaction in `_copy_button_extract`. Wider than just the pbcopy/pbpaste calls because `Meta+V` follows OS focus and ChatGPT's Copy-button onClick uses `navigator.clipboard.writeText` which needs document focus. Two parallel workers must NOT interleave these phases — they will silently swap each other's prompts/responses through the global macOS pasteboard. **Narrowing this lock to just `pbpaste` is wrong.**
- **Each worker creates its own tab via `ctx.new_page()`** in `_run_with_browser`. On exit it `await page.close()` — only its own tab. `await browser.close()` is explicitly NOT called: it's been observed to terminate the shared Chrome via CDP under some Playwright versions, which would kill every other worker's tab. The Playwright `async with async_playwright()` exit handles disconnect cleanly without killing the connect-over-cdp browser.
- **The isolated Chrome channel stays alive across worker lifecycles.** The mac mini's GUI session hosts Chrome Beta indefinitely; workers connect, work, disconnect. Stable Chrome remains a separate app identity for normal Dock use and updates. Use `gpt-pro-relay close-chrome` to tear the relay browser down; the exclusive `ChromeActivityLease` makes normal teardown race-free without a refcount. No auto-teardown is implemented.
- **Worker tabs always come from `ctx.new_page()`, never `ctx.pages[i]`.** A persistent `--user-data-dir` surfaces session-restored phantom tabs in `ctx.pages` (no compositor surface — `Page.captureScreenshot` hangs forever waiting for a paint frame, although DOM/CDP/input keep working). A freshly-created tab in an already-foreground Chrome is windowed by construction, so workers never need to probe via `Browser.getWindowForTarget`. **Don't try to close the phantoms** — `page.close()` on `chrome://omnibox-popup` hangs; leave them, they're harmless background orphans. Symptom of regression: every `screenshot_skipped` line in `worker.stderr` with `"waiting for fonts to load... fonts loaded"` followed by timeout, plus the user can't see the chatgpt tab. If the symptom returns, check whether anyone reintroduced a path that picks from `ctx.pages` instead of calling `ctx.new_page()`.

## Conventions

- Python 3.11+, `uv` for env management. `uv venv` + `uv sync`. Never `pip` directly.
- Stdout = response. Stderr = newline-delimited JSON. Don't mix them — the SSH UX depends on this split.
- Artifacts go to `~/.gpt-pro/runs/<run_id>/`. The run_id is caller-supplied via `--run-id` (recommended) or auto-generated.
- Profile dir is `~/.gpt-pro-profile/` — outside the repo, never committed.
- Browser app defaults to `/Applications/Google Chrome Beta.app`; override with `GPT_PRO_CHROME_APP` only for a recognized side-by-side Chrome channel. Never point it at Stable Chrome (`com.google.Chrome`).
- Worker spawned via `[sys.executable, "-m", "gpt_pro.cli", "_run", run_id]` so it works regardless of how the parent was invoked.

## ToS reality

Browser automation against ChatGPT violates OpenAI's terms. The user accepts the account-ban risk for personal use. Don't suggest making this multi-tenant or productizing it.

## What is intentionally NOT built

So future-Claude doesn't reflexively add it:

- Network-side completion signals (`async-status`, `implicit_message_feedback`, etc.) — the DOM-side Copy-button gate covers the same moment with a simpler implementation and no race against Playwright response-event timing. Wire one only if the Copy button selector itself becomes unstable.
- Auto-retry on errors — fail closed, surface the `run_dir`, let the user decide. Especially do NOT auto-retry on CDP disconnect (shared-Chrome crash) — re-submitting burns another 5–20 min of Pro reasoning, and a crash that recurs would multiply usage.
- `launchd` keepalive — `tmux` is fine.
- Sleep / clamshell handling beyond `caffeinate` — out of scope.
- Worker liveness check / orphan detection — if the worker dies before writing `result.json`, the parent waits indefinitely by default (or until an explicitly supplied parent-side `--generation-timeout`). Acceptable for now. (`RunClaim` is **not** this and doesn't change it: it never asks whether a worker is alive, only lets at most one *own* a run_dir. It also isn't the rejected refcount — it stores no count to corrupt, and the kernel drops a flock on process death, so a SIGKILLed worker leaves nothing stale.)
- **Refcount-based Chrome teardown** — was considered (option C from the multi-tab design review) and rejected. Cross-process refcount on `flock` is fragile to SIGKILL'd workers and adds exactly the kind of "small database" the no-SQLite invariant warns against. Manual `gpt-pro-relay close-chrome` is the supported teardown path; Chrome lives indefinitely otherwise.
- **Per-tab `_kill_chrome_orphans()` on every run** — the old `BrowserLock` ran it on entry. The new flow only runs it on the launch path (when CDP probe fails inside `LaunchLock`), so it cannot terminate the shared Chrome out from under live tabs. Putting it back on the connect path defeats multi-tab.
- **Auto-rate-limit detection / backoff** — if `network.json` starts showing 429s, captcha redirects, or unexplained `needs_reauth` after parallel bursts, that's account-side anti-abuse and the response is to drop `GPT_PRO_MAX_PARALLEL` to 1 (effectively the old serialized behavior), not to add code. (Distinct from the auto-dismiss of the "Too many requests" *conversation-history* modal — that just clicks "Got it" to clear a blocking UI overlay and never retries or re-sends; see *Other fragile assumptions*. Do **not** generalize it into send-retry/backoff on the generation endpoint.)
